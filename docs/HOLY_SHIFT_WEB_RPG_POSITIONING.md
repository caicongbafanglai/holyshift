## 1. 一页产品定义

### 1.1 产品定位

`Holy Shift 1.0 MVP` 是一款无需安装、无需登录、面向现代桌面浏览器的简体中文 3D RPG。玩家以第三人称或第一人称自由探索紧凑圣岛，在确定性的回合制战斗中观察敌人意图并选择攻击、防御或圣术，通过装备与成长选择变强，最终击败 Boss，并让圣堂状态在当前本地存档中持续保持。

### 1.2 目标玩家

- 内部目标画像：`16+`；这不是官方年龄评级或合规结论。
- 经验：理解生命值、攻击、防御、技能等基础 RPG 概念，不要求硬核刷宝经验。
- 动机：希望无需下载安装，在桌面浏览器完成一段短小、有明确成长反馈的 RPG 体验。
- 场景：单人、键盘与鼠标、一次 `20–35` 分钟；刷新页面后可从安全检查点继续。
- 首发语言：简体中文。

以下人群不是本版本的主要目标：期待大型开放世界、即时动作战斗、长期刷宝、多人竞技、移动端专项体验或持续运营内容的玩家。

### 1.3 可验证的核心承诺

> 玩家无需登录即可在 `20–35` 分钟内完成“任务 → 普通战 1 → 武器选择 → 普通战 2 → 圣物与属性成长选择 → Boss 战 → 世界变化”的三战闭环；两场普通战逐步教授敌人意图，Boss 战要求玩家在攻击、防御和圣术之间作出有效选择。

核心承诺成立必须同时满足：

1. 新玩家能够理解当前目标、敌人下一步行动和自己选择造成的结果。
2. 装备或成长选择会改变后续战斗中的可观察数值或策略。
3. Boss 在全部 `8` 种合法 Must 成长组合下都不能只靠连续普通攻击获胜，并且每种组合至少存在一条包含防御和圣术的通关路径。
4. 通关后圣堂的视觉或文本状态发生明确变化。

### 1.4 体验支柱

1. **快速进入**：无账号、无安装，新玩家不超过两次操作进入游戏流程。
2. **信息清楚**：目标、敌人意图、技能代价、伤害和状态变化始终可见。
3. **短而有决策**：不依赖实时反应；关键回合存在可解释的攻、防取舍。
4. **成长可感知**：奖励选择立即改变属性、行动效果或后续战斗策略。
5. **范围克制**：优先完成一个可靠闭环，不用更多地图、职业或资产掩盖核心玩法问题。

### 1.5 核心循环

```text
开始游戏
  → 圣堂接取唯一主线任务
  → 以第一/第三人称沿朝圣径自由探索
  → 观察敌人意图并进行回合制战斗
  → 从两项奖励中选择一项
  → 装备或属性成长
  → 解锁下一段区域与世界状态
  → Boss 战
  → 圣堂状态变化与结局
```

- 胜利：结算奖励、自动存档并解锁下一段探索目标。
- 失败：重开当前战斗；保留进入该战斗前的合法进度，不丢档、不倒扣资源。
- 完成：击败 Boss、返回圣堂并展示可识别的结局状态。

### 1.6 商业、联网与数据边界

- MVP 免费，无广告、支付、商城或抽卡。
- 游戏为单机体验；联网仅用于下载静态页面和资源。
- 不提供账号、云存档、跨设备同步、排行榜或多人功能。
- 不接入用户分析、行为追踪或第三方运行时广告脚本。
- 存档只保存在本地浏览器；清除或重置浏览器数据会删除存档，界面必须提前说明。

## 3. 游戏规则与内容预算

### 3.1 基础战斗规则

- 单个玩家角色对单个敌人，双方只有整数生命值 `HP`、力量 `POW` 和护甲 `ARM`。
- 玩家永远先行动。每回合按“展示敌人意图 → 玩家行动 → 若敌人存活则执行敌人行动 → 清理本回合状态 → 生成下一意图”的顺序结算。
- 所有伤害统一按以下顺序计算：`raw = floor(攻击方 POW × 行动倍率)`；`afterArmor = max(1, raw - 防守方 ARM)`；若防守方有防御状态，则最终伤害为 `max(1, ceil(afterArmor × 50%))`，否则等于 `afterArmor`。
- 玩家每回合选择一个行动：
  - **普通攻击**：行动倍率为 `1.0`，并获得 `1` 点信仰。
  - **防御**：获得防御状态并获得 `1` 点信仰；状态在下一次敌方伤害结算后失效，重复防御只刷新、不叠加。
  - **圣术**：消耗 `2` 点信仰，行动倍率为 `2.0`。
- 信仰少于 `2` 时，圣术控件必须显示不可用状态和可感知原因；鼠标、键盘或程序入口触发该行动都必须被拒绝，且不消耗回合、不改变任何战斗状态。
- 信仰每场战斗从 `0` 开始，上限为 `3`，不跨战斗保留；已满时继续获得不会溢出。
- 敌人只使用三种行动：普通攻击倍率 `1.0`、蓄力重击倍率 `1.6`、防御。敌方防御状态在下一次玩家伤害结算后失效，重复防御只刷新、不叠加。
- 每个敌人使用受版本控制的固定循环行动序列，并在内容数据中登记起始位置；战败重试从同一起始位置重新开始，不允许 UI 代码暗改序列。
- 敌人下一回合的行动类型、伤害预估或防御效果在玩家选择前可见。敌人意图在回合开始后不得无提示改变。
- 玩家行动击败敌人时，本回合立即胜利，敌人不再行动；双方同回合死亡不是合法结果。
- 战败恢复进入该战斗前的快照并重开当前战斗；不能重复领取已经结算的奖励。
- 1.0 的战斗与掉落默认确定性，不包含暴击、闪避或随机伤害；自动测试必须对同一输入得到同一结果。
- 伤害、减伤、资源变化和状态必须以文字与数值反馈，不能只依赖颜色或动画。
- `POW`、`ARM`、生命值、重击倍率和敌人行动序列允许在 Gate 2 试玩后通过受版本控制的数据表调优；`1v1`、结算顺序、三行动、信仰资源和可见意图属于冻结机制。

### 3.2 1.0 内容预算

“Must 数量”是实现核心承诺的精确基线，不能自行减少；“含 Should 最大量”是执行全部 Should 后仍不得超过的上限。

| 内容 | Must 数量 | 含 Should 最大量 |
|---|---:|---:|
| 可玩角色 / 职业 | `1 / 1` | `1 / 1` |
| 圣堂主界面 / 任务 NPC | `1 / 1` | `1 / 1` |
| 主线任务 | `1` 条线性任务 | `1` 条线性任务 |
| 地图 | `1` 条主路径 | `1` 条主路径 + `1` 条可选侧路 |
| 强制战斗 / 可选战斗 | `3 / 0` 场 | `3 / 1` 场 |
| 普通敌人原型 / 精英变体 / Boss | `2 / 0 / 1` | `2 / 1 / 1` |
| 装备槽 / 固定装备 | `2 / 4` | `2 / 6` |
| 主线奖励选择 | `2` 次二选一 | `2` 次三选一 |
| 等级成长 | `1` 次二选一提升 | `1` 次二选一提升 |
| 剧情文本 | `600–1,200` 个中文字 | 不超过 `1,500` 个中文字 |
| 结局状态 | `1` 个通关后的圣堂变化 | `1` 个通关后的圣堂变化 |

第一场战斗后从两件武器中选择一件并自动装备；第二场战斗后从两件圣物中选择一件并自动装备，再从 `HP` 提升或 `POW` 提升中选择一次。未选择物品不可取回，也没有背包或换装界面。因此进入 Boss 前恰好有 `2 × 2 × 2 = 8` 种合法 Must 成长组合。

任何超过右栏上限的新增内容都必须先证明不会影响 Must、容量和核心循环验证，并通过正式变更控制。

### 3.3 Must 数值与行动数据 v0

这些数值用于产生唯一可实现和可自动验证的候选基线。Gate 2 可以通过留痕数据变更调优，但必须重新执行全部 8 种 Boss 组合测试。

| 对象 | `HP` | `POW` | `ARM` | 固定行动循环 |
|---|---:|---:|---:|---|
| 固定主角（初始） | `12` | `4` | `1` | 玩家选择 |
| 普通敌人 1 | `10` | `4` | `0` | 普通攻击 → 蓄力重击 |
| 普通敌人 2 | `14` | `5` | `1` | 防御 → 普通攻击 → 蓄力重击 |
| Boss | `20` | `7` | `2` | 普通攻击 → 蓄力重击 → 防御 → 普通攻击 |

| 选择位置 | 选项 A | 选项 B |
|---|---|---|
| 第一战后武器 | 晨刃：`POW +2` | 守誓锤：`POW +1, ARM +1` |
| 第二战后圣物 | 生命护符：`最大 HP +4` | 铁印：`ARM +1` |
| 第二战后成长 | 坚韧：`最大 HP +4` | 威能：`POW +2` |

- 启用 `S-03` 时，第一战武器池增加旅者杖（`最大 HP +4, POW +1`），第二战圣物池增加恩典石（`最大 HP +2, ARM +1`）。
- 每场战斗以当前最大 HP 的满血状态开始；胜利结算、成长和自动存档完成后再开放下一段探索目标。
- 最大 HP 增加时，当前 HP 同量增加，但不能超过新最大值。
- Boss 的验收脚本覆盖上述 8 种组合：只普通攻击全部失败；每种组合至少有一条同时包含防御和圣术的通关路径。
- 启用 `S-03` 时，Boss 回归扩大到 `3 × 3 × 2 = 18` 种组合，并使用相同的“纯普攻失败且存在防御+圣术通关路径”标准。
- Gate 2 调整任一表格数值或行动序列时，变更提交必须附 8 组合回归结果和理由。

## 5. 非功能要求与发布质量

### 5.1 目标环境

- 首发环境为支持 WebGL2、IndexedDB 与 Web Locks 的现代桌面浏览器；目标覆盖 Chrome/Edge、Firefox 与 Safari 的当前稳定版。
- 自动化最低覆盖 Chromium 与 Firefox 两个独立引擎；品牌 Chrome/Edge 和 Safari 的准确版本、设备与人工结果在正式发布记录中登记，不能用单一 Chromium 结果冒充全部浏览器。
- 基准窗口为 `1280×720` 和 `1920×1080`；布局在浏览器缩放后不低于 `640×360` CSS 像素时仍须完成核心流程。
- 候选最低设备为 `4` 核 CPU、`8 GB` 内存和集成显卡；Gate 1 `READY` 前必须登记唯一参考机 ID、厂商/型号、CPU、GPU、驱动、内存、磁盘、Windows build 和供电模式，未登记时 `DEP-05` 保持阻断。
- 输入：键盘与鼠标；核心操作不得只依赖悬停。
- 小于 `640×360` CSS 像素的视口必须给出明确提示，不能显示一个看似可用但无法完成的流程。

移动端、触屏和竖屏不属于 1.0 专项承诺。不支持 WebGL2、IndexedDB 或 Web Locks 的旧版桌面浏览器会显示明确阻断与恢复说明，不能进入一个无法可靠保存的流程。

### 5.2 性能预算

Gate 3 前必须提供 HTTPS 的生产等价静态托管（开发期 `localhost` 除外）：与候选发布相同的构建、路径、压缩和缓存头，并确保目标浏览器可使用所需安全上下文 API。测试使用登记的参考机、接通电源且固定供电模式，网络整形为 `10 Mbps` 下行和 `100 ms` RTT。

测量协议：

1. Chromium、Firefox 以及正式发布登记的品牌浏览器分别建立全新浏览器上下文，清空 HTTP 缓存、Service Worker、IndexedDB 和本地存储后执行 `20` 次冷启动。
2. 分位数使用 nearest-rank：排序后取第 `ceil(0.95 × n)` 个样本；所有原始样本一并保存，不能只报 P95。
3. 应用在圣堂界面完成首次绘制、主要按钮可聚焦且事件处理器可响应时记录 `hs-interactive` 性能标记；导航开始到该标记是可操作时间。
4. 压缩传输量使用 `PerformanceResourceTiming.transferSize` 求和：首次资源统计到 `hs-interactive`，完整会话统计到结局首次绘制；缓存命中和跨域资源单独列出。
5. 帧时间在固定 3D 探索路径预热 `10` 秒后，以 `requestAnimationFrame` 时间差采样 `60` 秒并计算 P95；软件 GPU 结果与硬件加速参考机结果分开报告。
6. 输入反馈对冻结的 30 次键盘/鼠标操作，测量事件进入处理器到下一次反映新状态的 paint。
7. 内存以 Chrome DevTools Protocol 的 `JSHeapUsedSize` 为口径，在完整会话每个主线阶段采样并报告峰值。
8. 存档耗时从发起 IndexedDB 读写事务开始，到事务 `complete` 事件结束，按冻结状态执行 `30` 次。

候选预算：

- 首次关键资源压缩传输量不超过 `3 MB`，完整一次游戏会话资源不超过 `8 MB`。
- `20` 次冷启动的 P95 可操作时间不超过 `5 秒`。
- 固定 `60 秒` 3D 探索场景的 P95 帧时间不超过 `33.3 ms`。
- 常规按钮操作到可见反馈的 P95 不超过 `100 ms`。
- 峰值 `JSHeapUsedSize` 不超过 `128 MB`。
- 自动存档在基准设备上的 P95 完成时间不超过 `250 ms`。

这些是待实际测量的验收目标，不是当前已经达标的事实。

### 5.3 稳定性与数据

- 每个目标浏览器的关键路径至少连续 `3` 次 E2E 通过。
- 新游戏、正常继续、战斗中刷新、奖励待选择时刷新、奖励后刷新、通关后继续、启用 `S-01` 时的精英胜利/刷新、IndexedDB 不可用、写入/配额失败、旧 schema 迁移、兼容/不兼容内容版本、当前记录损坏但备份有效、当前与备份均损坏、重置、第二标签页和主写标签页退出后接管的状态矩阵必须 `100%` 通过。
- 在冻结的目标浏览器、状态矩阵和关键路径内，不得出现未处理异常、白屏、软锁、坏档或进度静默丢失。
- 存档包含 `schemaVersion`、内容版本和结构校验字段。写入时在一个 IndexedDB `readwrite` 事务中把已验证的当前记录复制为 `backup`，再写入新 `current`；只有事务 `complete` 才显示保存成功，`abort/error` 不得覆盖旧记录。
- 读取时先验证 `current`；无效时读取 `backup` 并明确提示已恢复。两者都无效时只能提示安全重置，不能白屏或把坏记录写回。
- 每个已公开 schema 到当前 schema 都必须有迁移或明确拒绝路径。当前首次发布至少覆盖初始 schema、未知未来版本和缺字段记录。
- `schemaVersion` 只描述结构，`contentVersion` 绑定敌人、装备、任务和行动数据。读取时仅接受当前版本或版本控制兼容表中有确定迁移的旧版本；未知未来版本或无迁移的不兼容内容必须保留原记录、阻止继续并提供可复制的诊断信息与明确重置动作，不得用当前内容猜测加载或覆盖原档。
- 进入每场战斗前，必须原子写入 `activeBattle` 检查点，至少包含战斗 ID、进入时玩家/装备/任务快照、固定行动序列起点、内容版本和状态 `inBattle`。战斗内回合状态只保存在内存；刷新 `inBattle` 时从该检查点以相同起点重开同一战斗。
- 普通战胜利时，在展示奖励前以单个事务把检查点改为 `rewardPending`，并登记唯一奖励事件 ID 与必选字段。第一战必选字段为 `weaponId`；第二战为 `relicId + growthId`，两项在同一确认界面选完后才允许一次原子提交，未确认草稿不写档。刷新 `rewardPending` 必须返回同一组选择且清空未提交草稿，不能重打战斗或重复领取。
- 奖励确认事务必须一次性应用全部必选项、推进任务、把事件标为已消费并清除检查点；缺任一字段、重复事件 ID 或事务失败时不应用任何一项。Boss 胜利不创建奖励事件，而是原子写入 Boss 已击败、圣堂世界变化和 `endingPending`；刷新返回同一结局，确认结局后只消费该事件并清除检查点，不重复改变世界状态。
- 启用 `S-01` 时，精英胜利不进入 `rewardPending`：单个事务直接登记唯一 `eliteCompleted` 事件 ID、完成侧路节点、写入非战斗纪念标记并清除 `activeBattle`。事务失败则保持可重试的胜利结算界面且不应用任何字段；成功后刷新返回已完成侧路，重复事件不得再次推进或写入。战败或胜利事务前刷新仍按 `inBattle` 检查点重开同一精英战。
- IndexedDB 不可用时不得静默开始可持久化流程；中途写入失败时保留内存会话、持续显示“尚未保存”和重试/退出动作。
- 同一存档使用 Web Locks 的命名独占锁维持唯一主写标签页；未取得锁的第二标签页必须进入阻断提示或只读状态，不能并发覆盖。主写标签页关闭或崩溃并释放锁后，只读标签页可由用户明确触发接管；接管者必须先取得锁并重新读取、校验最新 `current/backup`，不得把自身缓存状态直接提升为可写。目标浏览器不支持锁接口时不得开始可持久化流程。
- 不承诺防作弊；本地存档可修改属于已接受边界，因为本版本没有多人、排行榜或真实经济。

### 5.4 可访问性与反馈

- 所有核心操作可由键盘完成，焦点顺序与视觉焦点清楚。
- `1280×720` 与 `1920×1080` 窗口分别缩放至 `200%` 后，按约 `640×360` 与 `960×540` CSS 视口验收；两者的核心操作和信息都必须可完成且不被遮挡。
- 伤害、状态、可用性和错误不能只靠颜色表达。
- 始终提供减少动态效果选项；只有实际包含音频时才必须提供静音和音量选项。所有存在的设置都须本地保存。
- 教程必须允许跳过，并可从帮助入口重新查看。

### 5.5 隐私、安全与许可

- 不收集电子邮件、真实姓名、设备指纹或行为分析数据。
- 1.0 不接收角色名或自由文本；固定主角和剧情文本均来自受版本控制的内容数据。
- 运行时不依赖未经登记的第三方 CDN 脚本。
- 所有代码依赖、字体、图片、音频和数据都必须记录名称、版本、来源、许可和用途；没有许可证据不得合入。
- URL 参数和本地存档都视为不可信输入，不允许动态执行代码。

## 6. 技术与工程基线

### 6.1 技术选型

- 语言：战斗、内容与持久化领域层使用严格 TypeScript；实时渲染、输入与 DOM UI 使用 ES2022 模块并由 ESLint 执行静态检查。
- 工程：Vite；Node.js 与包管理器版本在 `M-01` 脚手架提交中固定。
- 表现层：Three.js WebGL2 负责低多边形 3D 世界，HTML/CSS/DOM 负责 HUD、对话、奖励、战斗和设置；关闭实时阴影与后处理并限制像素比。
- 领域层：战斗、掉落、任务和成长使用与 DOM 解耦的纯逻辑模块。
- 内容层：敌人、装备、任务和文本使用可校验的数据定义，不散落在 UI 代码中。
- 随机性：1.0 默认没有运行时随机战斗或掉落；若数据层未来需要随机性，必须通过变更记录引入可注入的 seeded RNG，不得直接调用不可复现的全局随机源。
- 持久化：IndexedDB 单档、schema 版本、当前记录和最近有效备份。
- 测试：Vitest 覆盖纯逻辑与存档迁移；Playwright 覆盖桌面关键路径。
- 部署：纯静态构建；不得把开发服务器当作生产部署。

依赖的准确版本、许可证和锁文件只能在实际初始化时记录，本文不虚构“最新版”或已安装状态。

### 6.2 结构约束

建议目录职责如下，允许等价命名但不得混淆领域规则和界面：

```text
src/
  app/          # 启动、路由和流程编排
  domain/       # 战斗、任务、成长、掉落
  content/      # 敌人、装备、任务与文本数据
  persistence/  # 存档、迁移和恢复
  entities/     # 玩家胶囊、移动、跳跃、碰撞与安全复位
  world/        # 程序化 3D 世界、可走面、碰撞体与交互物
  ui/           # DOM 视图、输入说明与反馈
tests/
  unit/
  e2e/
```

### 6.3 Definition of Done

每个需求只有同时满足以下条件才可标记完成：

1. 代码和内容已进入 `dev`，对应需求 ID 可追溯。
2. 验收标准有自动化测试或可重复的人工证据。
3. `typecheck`、`lint`、单元测试和受影响 E2E 通过。
4. 无新增未登记的依赖、素材或许可风险。
5. 错误、空状态、刷新和恢复路径已覆盖。
6. 变更影响文档、存档 schema 或内容数据时，同步更新对应说明。
7. 无已确认的 P0/P1；残余 P2/P3 已登记责任人与期限。

### 6.4 Git 工作流

- `dev` 是集成与日常开发分支；功能分支从 `dev` 创建并合回 `dev`。
- `main` 只接收达到发布条件的版本，不直接进行日常功能开发。
- 每个提交只包含可解释的相关变更，并在说明中引用需求 ID。
- GitHub 网站当前默认分支是否为 `main` 不改变上述工作流；若要改远端默认分支，必须由仓库管理员单独执行。

## 7. 人员、容量、预算与里程碑

### 7.1 默认交付模型

本候选基线按以下最低资源条件制定：

- `1` 名具备 Web 开发能力的主责实施者，提供 `20` 个实施周、每周 `5` 个工作日、`1.0 FTE`；Gate 1 `PASS` 后，这些实施周、两个玩家测试证据周和七个正式评审周分布在至少 `29` 个日历周内，不能把证据或正式评审窗口算作实施时间。
- 第 4 节的 `50` 人日全部是 `DEV` 的实现、内容集成与开发者自测工作，不混入 `PO` 或独立 `QA` 工时。
- Gate 2–8 的七个正式 `T0–T+4` 窗口位于实施周之间，候选另为 `DEV` 预留每个 Gate 最多 `1` 人日、合计最多 `7` 人日的答疑与证据支持；该支持不计入第 4 节的 `50` 人日，也不能用于修改冻结构建或提前实现下一阶段。
- `PO` 至少另行承诺 `5` 个有效人日用于范围、内容、预算和测试组织；独立 `QA` 至少另行承诺 `8` 个有效人日用于用例、设备、复测和证据。两者必须分别登记，不能拿 `DEV` 余量替代。
- 玩家参与者和 14 席正式评审时长属于外部闸门资源，必须在 Gate 1 章程单独登记，不计入实现者产能，也不能由同一实现轨迹冒充独立证据。
- 不依赖长期加班；每周超过正常工作时间的投入不计入容量证明。

正式开工前必须把角色映射到真实负责人或可追责账号，并分别证明 `DEV / PO / QA` 的可用性。若无法确认上述投入，本计划自动失效并回到 Gate 1 准备，不得把 AI 可用性当作人力承诺。

### 7.2 容量计算

| 项目 | 计算 | 结果 |
|---|---:|---:|
| `DEV` 名义实施工作日 | `20 个实施周 × 5 日` | `100` 人日 |
| 候选有效系数 | `0.65` | 候选可用量 `65` 有效人日 |
| Must / Should | `42 + 8` | `50` 人日 |
| 候选计划负载 | `50 / 65` | `76.9%` |
| 候选容量缓冲 | `65 - 50` | `15` 有效人日 |

候选系数 `0.65` 的拆分假设是：实施周内计划与同步 `10%`、休假/不可用 `5%`、工具与维护 `5%`、缺陷与返工 `10%`、外部等待 `5%`，合计扣除 `35%`。正式 Gate 评审窗口不在这 `20` 个实施周或 `100` 个名义实施日内，按第 7.4 节另行进入日历。该系数不是历史产速或人员承诺，不能单独证明 Gate 1 的 `80%` 门槛已经满足。

Gate 1 `READY` 前必须用实际人员、可用日和过去相似工作的记录替换或签认该系数，并分别登记 `PO / QA` 资源。W2 再用实际投入与完成量校准；任一角色有效产能或总预测偏差超过 `15%` 时，立即停止 Should，执行第 10 节删减或重新准备 Gate 1。

## 10. 量化删减预案

当满足任一条件时，立即按顺序删除 Should：

- 里程碑预测延期超过 `15%`。
- 实际有效系数低于 `0.65` 或预测总工作量超过可用产能 `80%`。
- 任一关键依赖延迟超过 `3` 个工作日。
- Must 在同期已消耗计划容量的 `80%`，但完成率低于同期目标。

删减顺序：

1. 删除 `S-01`：减少 `3` 人日。
2. 删除 `S-03`：累计减少 `6` 人日。
3. 删除 `S-02`：累计减少 `8` 人日。

完整删减减少 `8 / 50 = 16%` 的候选工作量，落在 `15–20%` 范围，且不改变核心承诺。删完仍无法按容量完成时，只能延期、补充已确认产能或重新进行/重新打开 Gate 1；不得删除核心 Must、降低验收线或依赖长期加班。

- 至少 `4/5` 无口头提示完成战斗循环并说清目标、敌人意图和行动结果。
- 至少 `3/5` 出现继续、重试或主动尝试不同策略的预定义行为。
- 若任一指标恰好卡在 `4/5` 或 `3/5`、一个样本即可改变裁决，则使用相同预注册规则追加另一批 `5` 人；两批分别报告，并要求合计至少 `8/10` 与 `6/10`，不得看到结果后修改排除规则。
- 未达标时只调整或替换机制，不增加地图、剧情或美术掩盖问题。

### 11.2 Gate 3：垂直切片候选

- 使用与 Gate 2 不重复的至少 `6` 名新玩家。
- 至少 `5/6` 无现场帮助完成代表性端到端流程。
- 首次完整体验落在 `20–35` 分钟目标内；同时报告实际人数、比例和分布。
- 满足冻结性能预算，且按实际产速重估后剩余范围仍保留至少 `20%` 容量。
- 若结果恰好为 `5/6`、一个样本即可改变裁决，则按相同规则追加另一批 `6` 人；两批分别报告，并要求合计至少 `10/12`。

### 11.3 1.0 整体验收

- `M-01` 至 `M-10` 的验收与证据一一对应。
- 每个目标浏览器的关键路径连续 `3` 次通过。
- 存档与恢复状态矩阵 `100%` 通过。
- 无未关闭且已确认的 P0/P1。
- 资源、依赖和许可清单完整，没有来源不明资产。
- 生产构建、评审构建和发布候选哈希一致。
- 提供干净构建、静态部署、已知问题和回滚说明。

玩家测试只能使用真实参与者记录；AI 或模拟画像可以生成假设，但不能计入样本。

### 12.2 变更触发器

以下任一变化在首次 `PASS` 前必须更新候选并重新完成 Gate 1 准备；首次 `PASS` 后必须正式重新打开 Gate 1：

- 目标玩家、核心承诺、核心循环或 `20–35` 分钟时长改变。
- 改为即时动作战斗、大型开放世界、多人、多角色或移动端 Must；3D、双视角和紧凑自由移动已由 `2.1` 覆盖决定批准。
- 增加账号、云档、服务端状态、分析、支付或真实经济。
- 增加内容使冻结工作量超过确认产能的 `80%`。
- 更改存档模型、目标浏览器、最低设备或主要渲染架构。
- 需要未经确认的人员、资金、供应商、版权或长期运维。

### 12.3 决策优先级

发生冲突时按以下顺序处理：

1. 安全、隐私、许可和数据完整性。
2. 核心承诺与不可删除 Must。
3. 性能、可访问性、测试和恢复能力。
4. Should 和视觉精修。
5. 新增功能或内容。

本候选基线的目标不是提前承诺一款大型 RPG，而是先用可验证、可回退、容量受控的范围证明 `Holy Shift` 的核心循环值得继续开发。
