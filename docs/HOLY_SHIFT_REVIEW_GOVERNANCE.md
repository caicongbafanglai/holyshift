## 一屏执行摘要

```text
7个正席  <->  7个镜像对抗席
正席举证达标；对席寻找真实缺口；双方使用同一标准。

开工前：冻结目标、权重、关键项、P0/P1和性能预算
提交时：冻结构建、版本、证据包、已知问题和风险
评审时：14席异步独立评分 -> 交换证据 -> 只审争议

PASS   总分>=85；关键项>=7；其余项>=6；无P0/P1
REVISE 75-84或可修复P1；只允许一次正式复审
OUT    总分<75、核心项<6、系统性P0或复审仍失败
DEFER  证据/人员/环境不足；限时补齐，不得视为默认通过
BUILD REJECTED  当前构建确认P0；先拒绝构建再做根因定界
VOID   版本或程序完整性失效；本轮作废，不给产品失败分

每条结论必须有：事实、证据、复现、影响、标准、验收。
没有证据的推测不扣分；虚构、隐瞒或篡改证据直接违规。
```

## 1. 使命、范围与基本原则

### 1.1 使命

本制度用于判断 `Holy Shift` 的每个开发阶段是否已经达到进入下一阶段的条件。它要同时解决四个问题：

1. 防止没有完成核心体验就扩大内容和成本。
2. 防止平均分、高层意见或会议气氛掩盖真实阻断项。
3. 让批评基于当前版本的事实，而不是虚构玩家、模糊感觉或事后改变标准。
4. 在保持审查强度的同时，通过异步取证、限时仲裁和明确退回路径控制评审成本。

### 1.2 适用范围

本制度适用于：产品范围、核心玩法、垂直切片、内容生产、系统补全、视听精修、测试优化、发布运营，以及会使已通过结论失效的重大变更。

普通开发任务和低风险缺陷不逐项召开全体委员会；它们在最近的阶段闸门中抽查，或使用本制度的轻量增量审查。

### 1.3 不可违反的原则

- **事实优先**：观察事实、专业解释和风险决策必须分开记录。
- **同标对审**：正席与对抗席使用相同需求、锚点和证据规则。
- **独立先行**：交换观点前先独立试玩、取证和密封评分，减少锚定与从众。
- **尖锐但克制**：可以直接指出失败，但只批产品和流程，不攻击个人。
- **不得虚构**：禁止虚构玩家反馈、数据、法规、竞品表现、测试结果或复现过程。
- **缺席不等于同意**：未完成的席位必须由替补补齐，不能默认为通过。
- **分数不是事实**：分数用于汇总；证据、红线和强制验收项决定能否放行。
- **OUT 有边界**：OUT 否决当前阶段方案，不自动删除整个项目或所有可复用资产。
- **规则不追溯**：阶段开始后不得为当前结果临时改权重、门槛或定义。
- **安全与合规优先**：安全、隐私、版权、评级和平台阻断不得用商业期限豁免。

## 2. 7×2 镜像委员会

### 2.1 席位结构

| 正席 | 镜像对抗席 | 共同负责的事实域 | 对抗席重点查漏 |
|---|---|---|---|
| 制作人 | 范围/成本审计席 | 范围、容量、预算、依赖、日程 | 乐观估算、范围漂移、隐性依赖、长期加班和沉没成本 |
| 游戏总监 | 创意一致性审查席 | 核心承诺、体验支柱、叙事与系统一致性 | 概念自相矛盾、功能漂移、同质化和“未来会好玩”的空头承诺 |
| 玩法/关卡席 | 漏洞/破局测试席 | 核心循环、关卡节奏、规则和可重复性 | 软锁、跳关、唯一最优解、机制绕过、死路和反馈误导 |
| 玩家体验席 | 新手/无障碍审查席 | 操作、引导、信息架构、可访问性 | 新手误解、输入障碍、认知负担、晕动风险和失败恢复困难 |
| 美术/音频席 | 视听质量审查席 | 视觉语言、声音、动画、反馈和资产一致性 | 可读性下降、风格冲突、缺失反馈、混音遮挡、资产性能与授权 |
| 技术/QA席 | 性能/稳定性审计席 | 构建、架构、测试、兼容、性能和数据完整性 | 崩溃、坏档、边界条件、回归、最低配置和不可复现构建 |
| 玩家/发行席 | 市场/合规审查席 | 目标玩家、产品表达、平台、发行和支持 | 宣传失真、受众错配、版权/隐私/评级风险和无法回滚的发布 |

### 2.2 正反席不是“支持者”和“反对者”

- 正席负责证明阶段目标已经达到，并主动披露已知风险；不得为了过关护航。
- 对抗席负责寻找真实缺口和反证；不得以制造问题数量或 OUT 数量为目标。
- 两席都可以给高分或低分，结论必须能够追溯到同一套冻结标准。
- 同一问题只指定一个主责事实域扣分，其他席位引用该问题，不得重复扣分。
- 跨领域问题由流程秘书指定主责组；阻断效力仍对整个闸门生效。

### 2.3 主席、流程秘书和仲裁组

- **主席**：默认由制作人正席主持，只管理议程、时限和程序，不得改分或单人否决。涉及制作人组争议时，由预登记替代主席主持。
- **流程秘书**：非投票角色，维护构建版本、证据索引、席位与替补、回避、原始评分、修改记录和最终裁决。
- **仲裁组**：由三名未涉事、无利益冲突的委员组成，至少包含一名正席、一名对抗席和一名相邻领域专家。阶段开工前登记仲裁池及固定轮换或可验证随机规则，主席不得自由挑选。仲裁以 `2/3` 形成书面决定。

### 2.4 任职、替补和能力要求

- 每个席位在阶段开始前登记主审与合格替补；开始评审后不得因分数不利临时换人。
- 同一正反对席必须由不同审查主体承担。内容负责人可以提交正席“负责人自评”，但它不算独立验证；本人不得独立复测或仲裁相关争议。对抗席必须与产出责任、汇报线和过关奖金独立。
- 同一自然人或同一责任主体每个闸门最多计一个有效席位；可以跨领域提供意见，但只能计一次评分和一次法定人数。替补不得是当前 14 席之一。
- 委员必须能使用当前构建、理解本领域标准并提交可复核证据；无法访问构建或缺乏必要能力时应主动回避。
- 每两个阶段至少轮换一次对抗席，降低固定立场、关系压力和盲区固化。

### 2.5 利益冲突与回避

评审前每席必须提交利益冲突声明。

| 冲突类型 | 示例 | 处理 |
|---|---|---|
| 职责性偏见 | 参与过被审内容、曾批准相关方案 | 可以陈述事实和评分，但不得仲裁该争议 |
| 实质性冲突 | 奖金与过关日期挂钩、直属利害、供应商或经济关系 | 必须回避，由替补独立评分 |
| 能力或访问冲突 | 无法运行构建、缺少设备、不了解适用标准 | 回避或仅提交明确标注的非裁决意见 |

未披露的实质性冲突一经确认，相关评分失效并重新评审。提交者可以答辩，但不能选择仲裁人、修改标准或压制异议。

## 3. 阶段闸门运行流程

### 3.1 状态机

```text
DRAFT -> READY -> FROZEN -> REVIEW -> RECONCILE -> DECIDE
                                                    |
      PASS / REVISE / OUT / DEFER / BUILD REJECTED / VOID <-+

疑似紧急P0：任意状态 -> HOLD -> 24小时内定级并返回裁决流程
```

- `PASS`：允许进入下一阶段。
- `REVISE`：当前方案可修，生成封闭整改清单并只允许一次正式复审。
- `OUT`：当前阶段方案失败，回到最近有效基线，缩范围、更换方案或终止该功能。
- `DEFER`：因证据、人员、版本或环境不足暂不能裁决；不是通过或失败，不消耗复审次数。
- `BUILD REJECTED`：当前构建确认存在 P0，立即拒绝该构建；根因分析后再决定局部修复重提还是扩大为阶段 OUT。
- `VOID`：版本或程序完整性失效，本轮作废并重新冻结；不得把委员或流程错误记成产品低分。
- `HOLD`：疑似 P0 的临时风险隔离状态，不是正式结论。

### 3.2 阶段启动：先冻结评审章程

开工前由主责正反席共同起草，委员会确认以下内容：

- 阶段目标、范围内和范围外事项。
- 强制交付物、验收用例和 Definition of Done。
- 评分维度、权重、行为锚点、关键项和最低项。
- 目标平台、设备矩阵，以及测量场景、采样时长、工具、P95 帧时间、峰值内存、冷/热加载口径和预算。
- 玩家测试对象、方法、样本用途和停止条件。
- `P0/P1` 阻断定义、已知风险和删减方案。
- 证据格式、构建冻结时间、评审日程、主审和替补。

章程的目标、权重、锚点、阶段阻断条件和强制项必须在阶段开工前冻结。只有新增的安全、法律、平台强制要求可以中途触发紧急变更；其他变更从下一阶段生效。`T-3` 以后出现任何实质标准变化，都必须重置阶段基线和评审日程，不能继续原评审。

### 3.3 提交包完整性检查

正式评审前，提交方必须提供：

- 构建号、构建哈希、生成时间、目标平台和测试环境。
- 阶段验收项与证据编号的一一对应表。
- 变更清单、已知问题、剩余风险和自评结果。
- 原始测试日志、性能数据、截图、录像及复现脚本。
- 第三方资产、字体、声音、代码和数据的许可清单。
- 上一轮问题的关闭证据和必要回归范围。
- 可重复构建说明、回滚点和负责人员。

**Gate 1 材料例外**：阶段 1 审查产品范围和计划，在工程尚未初始化时，以候选需求文档的 Git 提交哈希作为被审版本。构建号、运行日志、性能、运行时许可、回滚和构建复现材料可在 Gate 1 章程中逐项标为 `N/A`，但必须写明“不适用原因、首次适用阶段、责任人和到期时间”；不得虚构空构建或把别的工作区证据拼入提交包。Gate 1 仍必须提供目标玩家、核心承诺、Must/Should/Won't、逐项负责人/估算/验收、真实人员与产能依据、预算、设备、依赖、风险、删减预案、候选提交哈希、变更记录和自评。

Gate 1 `PASS` 前不得开始正式产品范围实现。为取得估算或依赖证据，章程可预登记一个最多 `2` 个实施人日、单独标识且可整体丢弃的 pre-Gate spike；其代码不得计入 Must 完成度、不得作为 Gate 2 白模或既有产品资产。

秘书只做完整性检查，不评价质量。包不完整时在 `READY` 前退回，不得启动计时或用缺失材料换取 DEFER。

### 3.4 标准评审节奏

| 时间 | 动作 | 时限 |
|---|---|---:|
| 阶段开工前 | 冻结目标、权重、锚点、关键项和阻断条件 | 不计入评审 SLA |
| `T-3` | 确认席位、替补、日程、构建窗口和材料要求 | 评审前 3 个工作日 |
| `T-1` | 完成提交包完整性检查 | 1 个工作日 |
| `T0` | 冻结构建和证据包 | 不得热更新 |
| `T+2` | 14 席完成独立试玩、取证和密封评分 | 2 个工作日 |
| `T+3` | 正反席交换证据、复现和纠正事实 | 1 个工作日 |
| `T+4` | 仅争议项进入裁决会并发布决定 | 1 个工作日 |

正式评审 SLA 从 `T0` 到 `T+4`，默认不超过 `5` 个工作日；章程冻结不计入该周期。阶段章程必须预先冻结每席评审时长预算，大型闸门可以在开工前采用更长 SLA，但不得在 `T0` 后因结果不利延长。低风险增量审查可缩短时限，但不得降低证据和回避要求。

### 3.5 异步优先和会议边界

- 14 席先异步工作；全员不为展示、背景介绍或逐条念报告开会。
- 事实一致且结论一致的项目自动进入记录，不上会。
- `P2/P3` 重复项由秘书合并，指定一个主问题编号。
- 会议只处理未解决的 `P0/P1`、跨越裁决线的评分和标准解释争议。
- 标准争议会默认上限 `30` 分钟；超时仍缺证据则进入限时 DEFER，不得靠妥协分数结案。

### 3.6 法定人数和缺席

- 最终 PASS 必须有七组完整报告，即 14 席均已提交或由预登记替补补齐。
- 沉默、弃权、超时和“无意见”都不等于同意；“未发现问题”必须附已执行的覆盖范围。
- 争议会至少 `10/14` 席到场，受影响正反席和三名仲裁员必须到场。
- `T+2` 未提交即自动启用替补，替补须在 `4` 小时内接管；无法补齐时只能 DEFER，不能按低分 OUT 或默认 PASS。
- 同一闸门的 DEFER 累计上限为 `2` 个工作日，重新排期不重置。仍缺席时升级给独立治理负责人补位并处理人员失职；产品不得因行政缺席被 OUT，也不得被缺席者持续否决。

### 3.7 构建冻结和证据失效

- `T0` 后禁止修改被审构建。任何代码、配置或资源变化都生成新构建号。
- 修复后只复用仍然适用的证据；受影响用例、性能结果和截图必须重新验证。
- 不同构建的证据不得拼接成一个“完整通过”结论。
- 无法重新生成的证据必须说明原因、来源和可信限制。

## 4. 事实与证据制度

### 4.1 每条结论的五层结构

1. **事实**：在什么版本、设备、位置和条件下发生了什么。
2. **证据**：日志、录像、截图、测试、测量或正式规则在哪里。
3. **解释**：该事实违反哪一条冻结标准或评分锚点。
4. **风险**：影响对象、范围、概率、持续时间和可恢复性。
5. **验收**：满足什么客观结果才算修复并关闭。

“我感觉不好”“玩家不会喜欢”“行业都这样”不构成事实。它们只能被改写为可验证假设，进入待验证池。

### 4.2 证据等级

| 等级 | 定义 | 裁决效力 |
|---|---|---|
| `E0` | 看法、猜测、无法定位的反馈 | 只能形成待验证假设，不扣分、不阻断 |
| `E1` | 绑定版本的一次观察、截图或录像 | 可触发复测，不能单独确认 P0/P1 |
| `E2` | 可复现步骤、日志、自动测试或有方法说明的测量 | 可支持评分和确认 P1 |
| `E3` | 独立复现、有效样本研究、取证材料或权威合规依据 | 可确认 P0 和正式否决 |

一份足够确定的安全、数据损坏或法律取证材料，经技术/QA或合规主责组签认后，可以直接作为 `E3`，不要求为了复现而扩大现实风险。

### 4.3 举证责任

- 声称“已经达标”的正席负责证明所有强制验收项已经完成。
- 声称“存在缺陷”的对抗席负责证明缺陷存在并说明影响。
- “没有发现问题”只有在预先声明的测试覆盖已执行时才是有效结论。
- 修复关闭证据不得低于原问题的证据等级；P0/P1 必须由非修复者复测。
- 法律、版权、平台政策和市场事实必须引用当前有效的正式文件、原始数据或合格专业意见，不能凭记忆裁决。

### 4.4 问题记录格式

每个问题必须包含：

```text
问题ID / 标题
构建号与哈希
环境、设备、时间
对应需求或评分锚点
实际结果 / 预期结果
复现步骤与发生频率
原始证据路径或来源
影响对象、范围与可恢复性
严重度（P0-P3）与置信状态
建议验证方法（不是强制实现方案）
关闭条件与回归范围
主责组、责任人、期限、状态
```

### 4.5 偶发问题和概率

- “不能每次复现”不等于不存在。必须记录运行次数、命中次数、环境差异、日志和影响。
- 严重度与置信度分开：低频坏档仍可能是 P0；高频轻微错位不自动升级为 P0。
- 无稳定步骤但有多轮日志支持的问题可标为“较可能”，触发限时调查或 HOLD；不能直接当作已确认 P0。
- 测试次数和环境矩阵必须在阶段章程中预先声明，避免看到结果后选择有利样本。

### 4.6 玩家研究与外部数据

- 真实玩家记录必须说明招募条件、预注册有效样本数、排除规则、任务、成功定义、版本、环境、主持干预、原始记录和退出样本。
- 小样本定性测试用于发现问题，不得包装成统计普遍性或市场需求结论。
- 同时报告人数和比例，例如 `4/5（80%）`，不得只给百分比制造精确感。
- 玩家画像、模拟用户和 AI 角色可以产生测试假设，不能冒充真实玩家证据。
- 涉及个人数据时遵守最小收集、知情同意、匿名化、访问控制和保留期限。

### 4.7 AI 审查特别规则

- AI 委员必须区分“通过工具实际验证”“从代码/材料推断”和“尚未验证”。
- 没有运行构建、读取日志或取得原始材料时，不得声称已经试玩、复现或采访玩家。
- AI 生成的玩家反馈、法规、竞品数据和引用不能作为事实证据。
- 共享模型、操作者、提示、上下文或同一执行轨迹的 AI 席位视为一个相关决策源；可以覆盖多个角色视角，但不能形成多份独立证据或重复计入独立确认。
- AI 参与法定人数时必须登记独立性矩阵。相关 AI 输出可以覆盖多个角色，但只能计一个有效席位和一次法定人数；P0/P1 的独立确认必须来自不同执行轨迹、环境或真实责任人签认，仅改变角色提示不构成独立复现。
- 涉及真实玩家体验、法律合规、平台政策和现实安全时，AI 意见只能辅助，必须由相应真实证据或合格责任人确认。

## 5. 严重度、置信度与红线

### 5.1 严重度定义

| 等级 | 定义 | 默认处置 |
|---|---|---|
| `P0 致命` | 无法启动/完成核心路径、坏档或数据丢失、广泛崩溃、严重安全隐私、明确版权/合规/平台阻断、现实安全风险 | 当前构建 BUILD REJECTED；立即隔离并做根因定界 |
| `P1 严重` | 主要功能或必经流程失效、严重性能不达标、目标玩家无法合理使用、系统性破坏核心循环、频繁但可恢复崩溃 | 阻止 PASS；进入 REVISE |
| `P2 一般` | 明显影响体验，但有合理绕过方式且不破坏核心流程 | 计入评分和缺陷预算 |
| `P3 轻微` | 外观、一致性或低影响问题 | 登记、排期或接受残余风险 |

严重度由影响、波及范围、可恢复性和发生概率共同确定，不由报告人单方面决定。

### 5.2 置信状态

| 状态 | 含义 | 可采取的裁决 |
|---|---|---|
| `已确认` | 达到对应证据等级并完成必要复核 | 可扣分、阻断或 OUT |
| `较可能` | 多项证据一致，但仍缺最终复现/取证 | 可 HOLD、DEFER 或要求补证，不能直接确认 P0 |
| `待验证` | 合理假设但证据不足 | 不扣分、不否决，进入验证池 |
| `已反驳` | 证据证明问题不存在、已失效或标准不适用 | 关闭并保留反驳记录 |

### 5.3 直接红线

以下情况无视总分，但必须区分产品失败、构建拒绝和程序作废：

- 已确认 P0：当前构建 BUILD REJECTED；只有系统性方案缺陷、合规阻断或正式复审再现时才扩大为阶段 OUT。
- 核心方案、生产可行性或合规关键项低于 `6/10`。
- 评审构建与交付/发布构建不一致、绕过法定人数或构建冻结：本轮 VOID，重新冻结，不给产品打失败分。
- 提交方故意隐瞒已知 P0/P1、伪造玩家反馈、篡改日志或选择性删除反证：当前提交 OUT，并启动治理调查。
- 委员造假或程序违规：排除相关证据、替换委员并重新评审；不得让产品替委员受罚。
- 使用未授权素材，或存在不可接受的数据、安全、隐私、评级和平台风险。

### 5.4 风险接受与豁免

豁免只能接受单项 P2/P3 残余风险。P0、P1、核心流程阻断、数据丢失、严重安全隐私、明确版权/平台阻断、评分门槛、关键项底线和强制交付物不得豁免；豁免不得改分或补足总分。

其他风险豁免必须记录：未达标准、业务理由、证据、影响、缓解措施、责任人、到期时间和回滚条件，并满足：

- 受影响正反席确认事实。
- 技术/QA或合规主责确认风险。
- 合格未回避委员向上取整的 `2/3` 同意，正反两侧分别过半，最低法定人数为 `10`。
- 申请人不参与批准。
- 最晚在下一闸门到期；没有下一闸门时必须给出正式发布前的绝对到期日。禁止自动续期。

阶段章程必须在开工前冻结 P2/P3 风险点算法、总上限、每域上限和到期规则。PASS 要求未超过预算、没有逾期 P2、没有同根因重复 P2；豁免项仍计入预算，不能借豁免清零。

## 6. 评分、校准与裁决矩阵

### 6.1 评分锚点

每项按 `0-10` 分，可使用 `0.5` 分增量：

| 分数 | 行为锚点 |
|---:|---|
| `0` | 证据已经证明该能力不存在或不可用；单纯材料缺失不得记 0 分 |
| `4` | 核本失败，不能完成该维度的基本目标 |
| `6` | 部分达到，但有实质缺口或未受控风险 |
| `7` | 达到冻结的最低验收线 |
| `8` | 稳定达到，只有可控的非阻断缺口 |
| `8.5` | 完整达到本阶段目标，证据充分且可重复 |
| `9` | 明显超出阶段目标，风险和边界得到验证 |
| `10` | 极少使用；有多源证据证明全面、稳定且显著超标 |

`85` 分 PASS 对应整体约 `8.5/10`，因此不是“勉强达到最低线”。

### 6.2 计算方式

- 每个阶段使用本制度第 8 节的默认维度和权重，权重之和必须为 `100`。
- 阶段启动时可基于项目事实调整权重，但必须在开发前冻结并记录理由。
- 加权总分：`SUM(维度分 / 10 × 维度权重)`。
- 标记 `★` 的关键维度必须至少 `7`；非关键维度默认至少 `6`，阶段章程只能提高、不能降低该底线。
- 每个维度在阶段开工前映射到唯一主责镜像组和交叉复核组，其他组可以提交交叉证据但不重复扣分。
- 七组都必须提交适用性报告；不适用项必须在开工前声明并同步冻结权重，不能在看到结果后临时标记 N/A 或重新分配。

### 6.3 正反席汇总

1. 两席先独立密封评分并引用证据编号；公开后原始分不得修改，只有留痕的笔误修正例外。
2. 公开后先纠正事实错误，再应用评分锚点，不得先谈“应该过还是不该过”。
3. 分差 `<=1`、事实一致且未跨越任何裁决线时，系统取未舍入的算术平均。
4. 其他情况，包括跨越 `6/7`、改变 PASS/REVISE/OUT、P0/P1 或事实争议，直接由仲裁组按锚点给最终分；双方不得另谈一个折中分。
5. 计算全程使用未舍入值，最终结果显示到两位小数。
6. 原始分、最终分、证据和裁决理由全部保留。

### 6.4 裁决矩阵

| 结果 | 必须满足的条件 | 后续动作 |
|---|---|---|
| `PASS` | 总分 `>=85`；所有关键项 `>=7`；非关键项 `>=6`；无未关闭 P0/P1；强制项全部完成；P2/P3 未超预算；七组报告齐全 | 锁定当前基线，进入下一阶段 |
| `REVISE` | 总分 `75-84.99`；或存在当前方案内可修复 P1/关键项不足 | 形成封闭整改清单，只允许一次正式复审 |
| `BUILD REJECTED` | 当前构建确认 P0 | 隔离构建并根因定界；局部首次回归可修复一次，重提计作唯一正式复审；系统性/合规/复审再现则阶段 OUT |
| `OUT` | 总分 `<75`；核心关键项 `<6`；系统性方案 P0；正式复审仍失败；或提交方严重造假 | 返回最近有效基线，缩范围、更换方案或终止功能 |
| `DEFER` | 证据、人员、构建或测试条件不足，且不存在已确认失败事实 | 限时补齐后恢复同一轮，不得无限拖延 |
| `VOID` | 构建、法定人数或程序完整性失效 | 本轮作废，纠正流程后重新冻结，不给产品失败分 |

不得设置“带 P1 条件通过”。时间压力、沉没成本和接近发布日期不是降低门槛的证据。

### 6.5 评分校准与防操纵

- 每个阶段前用同一示例构建或历史问题做一次评分校准。
- 连续偏高、偏低、频繁被仲裁推翻或证据质量不足的委员必须重新校准或轮换。
- 不以个人 PASS 率、OUT 数量、问题数量或平均分作为单一绩效指标。
- 禁止跨领域交换分数、压分邀功、高分护航、为避免仲裁故意把分差控制在阈值内。
- 分差只是仲裁触发器之一；任何事实争议、P0/P1 或裁决线争议都必须复核。
- 自报真实问题不处罚；隐瞒反证、夸大严重度、拆分重复问题和虚构反馈属于治理违规。

## 7. 仲裁、申诉、复审与变更

### 7.1 仲裁范围

仲裁只处理：事实是否成立、证据是否有效、标准如何解释、严重度和评分锚点如何应用。仲裁不负责替项目承担商业风险，也不能创造新验收标准。

### 7.2 仲裁流程

1. 秘书提交争议摘要、双方原始意见、证据索引和冻结标准；争议提出后 `4` 小时内按预登记规则组成仲裁组。
2. 仲裁组优先复现；不能复现时评估证据等级和缺失条件。
3. 双方各用相同时长陈述，不得引入未登记的口头证据。
4. 三名仲裁员在 `1` 个工作日内以 `2/3` 决定，并写明事实、依据、分数和影响。
5. 裁决写入记录，对本轮生效；不同意见可以保留，但不能阻塞执行。

### 7.3 申诉

- 只接受新的实质证据或明确程序错误，不接受对结果不满意的重复辩论；须在裁决后 `1` 个工作日内提出，并在 `2` 个工作日内完成。
- 每个争议最多申诉一次，并由不同的三人仲裁组处理。
- 申诉不自动暂停安全隔离和 P0 处置。
- 针对 PASS 的实质程序申诉在裁决前暂停基线晋级；其他申诉不自动暂停执行。
- 无法解决的证据缺口默认 DEFER/REVISE，绝不能因时间到期自动 PASS。

### 7.4 REVISE 和正式复审

REVISE 必须生成封闭整改清单：问题编号、责任人、修复范围、验收证据、回归范围和截止时间。

- 复审只检查整改项及必要回归，不重新开放已冻结标准。
- 新发现的 P0/P1 仍可改变结果。
- 同一方案只允许“初审 + 一次正式复审”。
- BUILD REJECTED 后的局部 P0 修复重提占用这一次正式复审机会。
- 再次失败必须缩范围、替换方案或终止该功能，不得只改版本名原样重提。

### 7.5 OUT 后的处理

OUT 后必须完成：

1. 确认退回到哪个最近有效基线。
2. 根因分析：目标错误、方案错误、执行失败还是证据不足。
3. 明确保留、返工和废弃的资产，禁止因情绪全部删除。
4. 重新冻结范围、方案、责任人和新闸门日期。
5. 若核心承诺或目标玩家改变，重新打开第 1 阶段。

### 7.6 变更控制和重新开闸

以下变化会使相关 PASS 失效并要求重新评审：

- 核心循环、目标玩家、商业模式或目标平台改变。
- 关键存档格式、网络/数据模型、输入方式或无障碍承诺改变。
- 性能预算、最低配置或主要渲染/物理架构改变。
- 垂直切片代表性、内容规模或发布声明发生实质变化。
- 新法规、平台政策、版权或安全事实使旧结论失效。

制度本身的变更须正反两侧分别过半且全席 `2/3` 同意，只对下一阶段生效；不得追溯改变当前结果。

## 8. 八阶段专属闸门

以下数字是默认最低线。第 1 阶段必须根据实际团队、目标设备和产品范围确认或正式调整；后续只能通过变更单修改。每份阶段章程必须列出“评分维度 -> 唯一主责镜像组 -> 交叉复核组”；七组都提交适用性报告，只有主责组产生该维度分。

小样本门槛只代表烟雾测试的最低信号，不证明市场普遍性。章程必须预注册样本、排除规则和采样顺序；当单个测试者就能改变裁决时，增加一个独立批次后再定结论。所有阶段阻断条件仍须满足第 5 节的证据与确认规则；疑似阻断先进入 HOLD，单次观察不能直接确认 P0。

### 8.1 阶段 1：锁定范围

| 项目 | 默认要求 |
|---|---|
| 主签 | 制作人 ↔ 范围/成本审计席 |
| 证据 | 一页产品定义、目标玩家、核心承诺、Must/Should/Won't、里程碑、人员/预算、依赖图、风险表、删减预案 |
| 评分 | 玩家承诺 `20`｜`★范围可行性 35`｜容量与计划 `25`｜风险与依赖 `20` |
| 最低线 | 每个 Must 有负责人、估算和验收；冻结的 1.0 总工作量不超过确认可用产能的 `80%`；不可删核心 Must 单列；另有从非核心范围降级/删除、可减少总工作量 `15-20%` 的预案 |
| 阶段阻断条件 | 目标玩家或核心循环说不清；依赖未确认人员、资金、版权或长期加班；关键依赖无验证计划 |
| 失败退路 | 缩范围、改平台或暂停项目，不得直接进入内容生产 |

确认可用产能必须基于“实际可用人员 × 有效工作日 × 有历史依据的有效系数”，并先扣除管理、评审、休假、维护、缺陷修复和外包等待；统计周期、数据来源和假设必须写入阶段章程。

### 8.2 阶段 2：核心玩法

| 项目 | 默认要求 |
|---|---|
| 主签 | 游戏总监 ↔ 创意一致性席；玩法/关卡 ↔ 漏洞/破局测试席 |
| 证据 | 可操作白模、输入说明、完整核心循环、原始试玩记录、问题清单、目标设备性能采样 |
| 评分 | `★核心乐趣 30`｜`★循环清晰 25`｜决策深度 `20`｜控制反馈 `15`｜技术可行 `10` |
| 最低线 | 章程预注册有效样本 `n>=5`、排除规则、任务与成功定义；`>=80%` 无口头提示完成循环并说清目标/结果；`>=60%` 出现预定义的继续/重试/主动探索行为或给出固定题目肯定回答；结果报告 `x/n` 和比例 |
| 阶段阻断条件 | 乐趣只存在于描述或未来美术；单一策略绕过核心决策；多数测试者持续误解反馈；核心技术无法满足冻结预算 |
| 失败退路 | 更换或删减机制，不得用新增地图、任务或美术掩盖核心问题 |

### 8.3 阶段 3：垂直切片

| 项目 | 默认要求 |
|---|---|
| 主签 | 游戏总监、玩家体验、技术三组共同签署 |
| 证据 | 约 `15` 分钟端到端构建、至少 `6` 名新玩家完整记录、性能轨迹、缺陷表、资产/关卡实际工时和生产复盘 |
| 评分 | `★完整体验 30`｜引导与节奏 `20`｜视听代表性 `15`｜`★稳定性能 15`｜`★生产可复制性 20` |
| 最低线 | 章程预注册有效样本 `n>=6`、排除规则和成功定义；`>=80%` 无现场帮助完成并报告 `x/n`；体验时长在冻结容差内；最低配置达到预算；按实测速率重估后剩余范围保留 `>=20%` 容量 |
| 阶段阻断条件 | 只能靠开发者演示；使用无法复用的一次性流程；崩溃、软锁或坏档；切片质量无法复制到剩余内容 |
| 失败退路 | 退回核心玩法或生产管线，不得扩大地图和内容 |

### 8.4 阶段 4：内容生产

| 项目 | 默认要求 |
|---|---|
| 主签 | 制作人、玩法/关卡、美术三组共同签署 |
| 证据 | 内容矩阵、内容 DoD、全流程构建、实际产速、缺口/占位清单和更新后的完工预测 |

## 9. 紧急处理与增量审查

### 9.1 P0/P1 响应

| 级别 | 确认收到 | 初步隔离/定级 |
|---|---:|---:|
| 疑似 P0 | `1` 小时 | `4` 小时隔离，`24` 小时内初步定级 |
| 疑似 P1 | `1` 个工作日 | `2` 个工作日内定级 |

P0 的小时级 SLA 只适用于已登记的线上值班窗口；非值班期从下一个工作窗口起算，并必须记录交接。相关正反席加技术/QA可以先发布紧急 HOLD，无需等待全员。HOLD 不能被用来无限暂停闸门。

### 9.2 紧急发布

只有安全、数据、隐私、合规或线上不可用问题可以走紧急发布：

- 先冻结事故版本和证据，明确回滚条件。
- 至少由技术/QA正反席和一个无冲突业务席签署。
- 只包含必要修复，不夹带普通功能。
- 发布后 `24` 小时内补齐增量评审，`48` 小时内完成复盘。
- 紧急流程不能豁免 P0、许可、隐私和构建一致性。

### 9.3 低风险增量审查

不改变核心循环、数据格式、平台、性能预算或玩家承诺的局部修复，可以申请增量审查。资格必须由相关正反席和技术/QA正反席共同签署，提交方不能自行降级分类。

涉及存档、权限、第三方资产、安全、构建链、性能预算或既有 P0/P1 根因时，强制完整重开闸门。任何审查组发现影响已通过基线时也立即升级；每阶段对增量 PASS 做预先冻结比例的随机审计。

### 10.2 运行指标

委员会按阶段观察组合指标，不给个人设置单一配额：

- 评审周期和按时提交率。
- 问题确认率、撤回率、重复率和复开率。
- 通过后逃逸的 P0/P1/P2 数量与来源。
- 仲裁推翻率、证据清晰度和评分漂移。
- REVISE 后一次通过率、OUT 后返工成本和范围变化。
- 测试覆盖、构建可复现率和风险豁免逾期率。

每两个阶段抽查一次 PASS 证据；所有 P0、OUT、豁免、证据违规和流程违规必须全量审计。

### 10.3 委员行为评价

委员质量看：复现准确率、严重度校准、逃逸问题、证据清晰度、时效和纠错意愿。不得按发现数量、OUT 数量、PASS 率或上线速度单独奖惩。

对抗席拥有免受报复的事实异议记录权，同时对虚假、夸大、隐藏反证和恶意拖延承担责任。

### 10.4 治理事件处理

评分操纵、证据造假、隐瞒反证、利益冲突未披露和报复异议统一进入治理事件流程：

1. 秘书登记事件并冻结相关记录。
2. 由独立三人调查组复核，被指控者及其汇报关系人员回避。
3. 调查只认书面证据，并给予当事人一次书面答辩和一次申诉。
4. 处置按事实依次为：纠正记录、排除证据、重新校准、替换席位、取消本阶段资格。
5. 只有故意造假、隐瞒或报复进入最高级处置；普通误判不得按恶意处罚。
